Opportunity Runtime — System Design & Task Prompts


1. Purpose


把定时任务从“每天给几个点子”升级为一个可持续运行的机会发现系统：


感知需求 → 标准化证据 → 去重/聚类 → 机会判断 → 最小实验 → 真实反馈。


核心原则：
- Google / Gemini 负责感知需求与注意力变化。
- GPT Scouts 负责抓取 Google 生态之外的痛点、摩擦、产品供给和开发者生态信号。
- Google Drive / Docs 是跨模型的异步消息总线，而不是知识库本身。
- Judge 不按“热度”决策，而按独立证据、付费/行为信号、供给缺口、个人优势、平台替代风险决策。
- Scout 可以高频，Builder 必须低频；每周最多批准 1 个新实验。
- 每次运行生成新文件，不多人追加同一个日报，保证可审计、可补跑、可回滚。

3. Shared Opportunity Card Schema


所有 Scout 输出候选机会时，都使用相同字段。不要为了凑字段而猜测；未知就写 Unknown。


Opportunity Card
- opportunity_id: 稳定 slug，围绕“人群 + Job To Be Done”，不要围绕某个具体产品名。
- title: 一句话描述机会。
- audience: 谁遇到这个问题。
- jtbd: 用户真正想完成的任务。
- geography: 国家/地区；未知则 Global/Unknown。
- signal_type: demand / pain / willingness_to_pay / supply_gap / platform_shift / workaround。
- why_now: 为什么现在值得关注。
- evidence: 每条必须包含 source、date、url、事实/短引文、evidence_type。
- independent_sources: 独立来源数量。转载、互相引用、同一项目不同页面只算一个来源。
- frequency_signal: 问题出现频率或重复程度；无法量化则 Low/Medium/High。
- commercial_signal: 价格、CPC、招聘预算、付费订阅、明确愿意付钱等；没有证据就写 None。
- current_workaround: 用户现在怎么解决。
- existing_supply: 已有 App/SaaS/开源项目/平台原生能力。
- supply_gap: 现有供给为什么仍然没解决好。
- platform_kill_risk: Low/Medium/High，并说明 Google/Apple/OpenAI/Anthropic/OS/大平台是否容易原生吃掉。
- experimentability: 是否能在 2–4 小时形成可验证实验。
- confidence: Low/Medium/High。
- disconfirming_evidence: 至少写一条可能证明这个机会“不值得做”的证据或解释。


4. Scheduling Strategy


以下时间按 Asia/Shanghai 举例。重点不是具体分钟，而是错峰，让下游只读取已经稳定落盘的文件。


05:30  Gemini — Google Demand Scout
06:00  Gemini — YouTube Intent & Pain Scout
06:30  Gemini — Geo / Trends Diffusion Scout
07:00  GPT — Reddit Pain Scout
07:20  GPT — App Store Friction Scout
07:40  GPT — GitHub Momentum & Gap Scout
08:10  GPT — Daily Opportunity Integrator
周六 09:00  GPT — Weekly Opportunity Judge
周六 09:30  GPT — Experiment Designer（仅在 Judge 批准实验时执行）


如果某个上游文件当天缺失，下游不要凭空补全。明确标记 source_missing，并继续使用其余证据运行。


Gemini 当前定时能力可调用已连接的 Google Workspace；为了降低失败耦合，每次要求“新建 Doc + 精确文件名”。如果不能放入指定目录，退化为在 My Drive 创建同名文件；GPT 下游应先查目录，再按精确前缀全盘搜索。


5. Gemini Task Prompt — Google Demand Scout


任务名：Opportunity Runtime — Google Demand Scout
建议频率：每天 05:30
输出：Opportunity Runtime/10_Gemini/Google-Demand/OR-GEMINI-DEMAND-YYYY-MM-DD


PROMPT


你的角色是 Demand Sensor，不是创业顾问。目标是发现过去 24 小时到 30 天内正在形成、加速或持续存在的真实需求，不要输出泛泛的“AI 趋势”。


优先使用 Google Search 以及当前 Gemini 可访问的 Google 生态公开信号。若 Google Trends、相关搜索、搜索建议或其他趋势数据在当前环境可用，则使用；不可用时不要伪造数值。


重点寻找：
1. 明显增长的新查询、新工作流、新产品类别或新术语。
2. “how to / alternative / automate / replace / best / cheaper / local / offline / export / sync / integrate”等具有任务意图的搜索。
3. 用户已经在用多个工具拼接完成的工作。
4. 新平台、新模型、新法规、新硬件带来的二阶需求。
5. 美国已成熟但其他地区仍供给不足的需求。


降低以下内容权重：纯新闻热度、名人事件、短期娱乐热点、没有明确 Job To Be Done 的 AI 概念、仅因媒体大量报道而上升的查询。


对每个候选，找到至少 2 条可追溯证据；如果只有 1 条，放入 Weak Signals，不进入主候选。


尤其关注这些问题：
- 用户真正想完成什么，而不是在搜什么产品名？
- 搜索增长是需求增长，还是新闻导致的注意力脉冲？
- 是否出现商业信号或高价值工作流？
- 平台是否很快会原生消灭这个摩擦？


输出最多 8 个 Opportunity Cards，按证据强度排序。最后增加：
- New Signals：今天首次出现且值得继续观察的信号。
- Persistent Signals：连续出现、证据正在增强的信号。
- Faded Signals：热度下降或被证伪的信号。


创建新的 Google Doc，标题严格为 OR-GEMINI-DEMAND-YYYY-MM-DD。优先存放到 Opportunity Runtime/10_Gemini/Google-Demand。不要修改历史文件，不要编造不可获得的搜索量或增长率。


6. Gemini Task Prompt — YouTube Intent & Pain Scout


任务名：Opportunity Runtime — YouTube Intent & Pain Scout
建议频率：每天 06:00
输出：Opportunity Runtime/10_Gemini/YouTube-Intent/OR-GEMINI-YOUTUBE-YYYY-MM-DD


PROMPT


你的角色是 YouTube Intent Sensor。YouTube 被视为“用户主动学习如何完成任务”的搜索引擎，而不是内容热榜。


分析最近 7–30 天内出现或明显升温的 how-to、setup、review、comparison、alternative、workflow、automation 类视频和相关搜索意图。


重点提取：
- 视频标题和搜索词揭示的 Job To Be Done。
- 评论区重复出现的问题、失败点、功能请求和 workaround。
- “有没有更简单的方法”“为什么不能自动做”“我现在需要 X + Y 才能完成”等摩擦。
- 新工具很受关注，但教程复杂、安装复杂、配置复杂的情况。
- 内容需求强，但高质量供给很少的 Demand–Supply Gap。


不要把高播放量自动等同于产品机会。优先关注：近期发布仍快速获得互动、多个创作者独立覆盖相似问题、评论存在重复痛点、用户主动询问工具/付费方案。


每条证据附 URL、发布日期或可见日期、可见数据。评论只引用必要的短句，其余用自己的话概括。


输出最多 8 个 Opportunity Cards，并额外给出 3 个指标：
- Content Demand：Low/Medium/High
- Product Supply：Low/Medium/High
- Demand–Supply Gap：Low/Medium/High


创建新的 Google Doc，标题严格为 OR-GEMINI-YOUTUBE-YYYY-MM-DD。优先存放到 Opportunity Runtime/10_Gemini/YouTube-Intent。不要修改历史文件。


7. Gemini Task Prompt — Geo / Trends Diffusion Scout


任务名：Opportunity Runtime — Geo Diffusion Scout
建议频率：每天 06:30
输出：Opportunity Runtime/10_Gemini/Geo-Trends/OR-GEMINI-GEO-YYYY-MM-DD


PROMPT


你的角色是 Geographic Diffusion Sensor。目标不是找“哪个国家增长最快”，而是寻找已在一个成熟市场验证、正在向其他语言或地区扩散，但当地产品/内容供给仍不足的需求。


优先比较：美国、加拿大、英国、澳大利亚、德国、日本、韩国、印度、东南亚、拉美，以及其他出现明显信号的市场。


寻找：
- 成熟市场已有成熟产品和付费行为，而另一地区搜索/讨论刚开始增长。
- 当地语言教程少、产品本地化差、支付/法规/文化流程不匹配。
- 全球 SaaS 能用，但当地用户仍依赖 Excel、WhatsApp、LINE、微信、邮件或人工流程。
- AI 让过去因市场规模太小而无法经济服务的细分市场变得可行。


若 Trends 数据可访问，使用实际趋势；若不可访问，使用 Google Search、YouTube、当地语言搜索结果等代理信号，并清楚标注 Proxy Signal，绝不伪造趋势百分比。


输出最多 6 个 Opportunity Cards。每个候选必须明确写：成熟市场、扩散市场、当地缺口、为何现在、最小验证方式。


创建新的 Google Doc，标题严格为 OR-GEMINI-GEO-YYYY-MM-DD。优先存放到 Opportunity Runtime/10_Gemini/Geo-Trends。不要修改历史文件。


8. GPT Task Prompt — Reddit Pain Scout


任务名：Opportunity Runtime — Reddit Pain Scout
建议频率：每天 07:00
输出：Opportunity Runtime/20_GPT/Reddit/OR-GPT-REDDIT-YYYY-MM-DD


PROMPT


搜索 Reddit 最近 7 天为主、必要时扩展到 30 天，寻找高质量的真实痛点与 workaround。目标不是总结热门帖子，而是发现用户反复试图完成但现有产品做不好的 Job To Be Done。


优先识别这些语言模式：
- is there a tool / app for...
- I wish...
- why can't...
- every time I have to...
- currently I use X + Y...
- manually...
- takes forever / tedious / annoying
- willing to pay / paid / subscription / expensive but...
- alternative to...


跨 subreddit 搜索，不要只盯 AI 和程序员社区。优先真实职业、家庭、教育、创作者、小企业、爱好者、跨境、本地服务等垂直社区。


去掉：纯抱怨、政治争论、一次性 bug、已有明显标准答案、没有重复性的需求。


同一帖子里的多个评论不算多个独立来源；跨帖子、跨 subreddit、跨时间重复出现才提高 evidence independence。


输出最多 10 个 Opportunity Cards，并保留原帖 URL。明确区分：Pain Evidence、Workaround Evidence、Willingness-to-Pay Evidence。


创建新的 Google Doc，标题严格为 OR-GPT-REDDIT-YYYY-MM-DD，存放到 Opportunity Runtime/20_GPT/Reddit。不要修改历史文件。


9. GPT Task Prompt — App Store Friction Scout


任务名：Opportunity Runtime — App Store Friction Scout
建议频率：每天 07:20
输出：Opportunity Runtime/20_GPT/AppStore/OR-GPT-APPSTORE-YYYY-MM-DD


PROMPT


搜索公开可访问的 App Store 产品页、评论、版本更新说明及相关网页索引，寻找“已有付费市场，但体验仍存在持续摩擦”的类别。


优先：
- 高评分/高知名度产品仍反复出现的 1–3 星痛点。
- 订阅价格不低，但用户仍需要手工补流程。
- 最近版本频繁修补同一问题。

重点判断“平台消灭摩擦的速度”：如果 Apple/Google 很可能在 OS 层直接补齐，Platform Kill Risk 要提高。


输出最多 8 个 Opportunity Cards，并为每个候选写：现有头部产品、反复摩擦、用户 workaround、可能的 wedge、平台风险。


创建新的 Google Doc，标题严格为 OR-GPT-APPSTORE-YYYY-MM-DD，存放到 Opportunity Runtime/20_GPT/AppStore。不要修改历史文件。

12. GPT Task Prompt — Weekly Opportunity Judge


任务名：Opportunity Runtime — Weekly Opportunity Judge
建议频率：每周六 09:00
输出：Opportunity Runtime/30_Judge/OR-JUDGE-YYYY-Www


PROMPT


你是 Opportunity Judge。读取最近 7 天的 OR-POOL-*，必要时回溯其原始 Scout 文档验证证据。


目标不是列出最多机会，而是决定：本周什么值得继续观察，什么值得验证，什么值得真正花时间实验，什么应该明确放弃。


硬门槛：
- 只有单一来源、纯新闻热度或没有具体 Job To Be Done 的候选，不得进入 Experiment。
- Experiment 候选原则上需要 >=3 个独立证据，且至少包含 Pain/WTP/Behavior 中的一类强信号。
- 最小实验必须能在 2–4 小时形成外部证据；无法做到则先设计验证，不直接 Build。
- 每周最多批准 1 个新实验。


100 分评分：
- Evidence Quality & Independence：20
- Pain & Frequency：15
- Commercial / WTP Signal：15
- Why Now / Momentum：10
- Supply Gap：10
- Personal Edge：10
- Distribution / Reachability：10
- Build Cost：5（越低越高分）
- Platform Kill Risk：5（风险越低越高分）


评分只是辅助。高分但证据质量差的候选必须降级。


特别考虑个人优势：终端/Android、AI Agent、开发者工具、自动化、手游/分发、数据分析，以及快速做软件 MVP 的能力。避免仅因为“AI 很热门”提高分数。


输出结构：
A. Executive Decision：一句话说明本周是否值得启动新实验。
B. Top 5 Opportunity Table：分数、阶段、证据强度、变化趋势。
C. #1 Opportunity Deep Dive：JTBD、用户、证据链、现有替代、为什么仍有缺口、平台风险、获客入口。
D. Disconfirming Case：最强反方论据，以及什么事实出现时应立即 Kill。
E. Decision：Experiment / Validate / Watch / Kill。
F. 若为 Experiment：给出一个 2–4 小时最小实验，不写完整产品计划。
G. What Changed：相比上周新增、增强、衰退和被证伪的机会。


创建新的 Google Doc，标题严格为 OR-JUDGE-YYYY-Www，存放到 Opportunity Runtime/30_Judge。不要修改历史报告。


13. GPT Task Prompt — Experiment Designer


任务名：Opportunity Runtime — Experiment Designer
建议频率：每周六 09:30
输出：Opportunity Runtime/40_Experiments/OR-EXPERIMENT-YYYY-Www-<slug>


PROMPT


读取本周 OR-JUDGE-YYYY-Www。只有当 Judge 明确标记一个机会为 Experiment 时才继续；否则输出“NO EXPERIMENT APPROVED”并结束，不为了保持产出而制造项目。


目标是设计最小可证伪实验，而不是 MVP 功能列表。

- 用户是否真的遇到这个问题？
- 是否愿意留下邮箱/付费/预约？
- 用户是否愿意从现有 workaround 迁移？
- 技术是否能把关键步骤从 10 分钟降到 1 分钟？


实验时间预算 2–4 小时；默认不超过一周副业时间的一半。优先：可点击 demo、非常小的 CLI/extension/shortcut、benchmark、landing page、手工 concierge test、问题访谈脚本、开源 Skill/Adapter。


输出：
- Hypothesis
- Riskiest Assumption
- Experiment
- Build Boundary：明确什么不做
- Success Metric
- Failure Metric
- Evidence Collection
- Time Budget
- Cost Budget
- Next Decision：Double Down / Iterate / Kill


第一阶段只生成实验方案和必要的可逆资产，不自动发送营销邮件、不购买广告、不产生付费、不代表用户公开发布内容。涉及这些外部不可逆动作时，留作人工批准点。


创建新的 Google Doc，标题严格为 OR-EXPERIMENT-YYYY-Www-<slug>，存放到 Opportunity Runtime/40_Experiments。


14. Anti-Noise Rules


整个系统必须遵守：
- 新颖性不是机会，重复出现且有行为证据才是。
- 多个模型看到同一新闻不算多条独立证据。
- Star、播放量、点赞只能证明注意力，不能证明付费需求。
- 明确的 workaround 往往比“我希望有一个 App”更有价值。
- 已经有人付钱但仍抱怨，通常比“大家觉得很酷”更值得验证。
- 平台能力即将原生覆盖时，提高 Platform Kill Risk。
- 每个候选必须记录反证，防止系统只会自我强化。
- Watchlist 不是失败；避免为了输出而启动项目。
- 每周只允许一个 Experiment，让真实世界反馈成为瓶颈，而不是模型生成速度。


15. Evolution / Memory


机会 ID 围绕 JTBD 保持稳定。Judge 每周要追踪：
- first_seen
- last_seen
- independent_evidence_count
- stage
- score_history
- strongest_evidence
- strongest_disconfirming_evidence
- platform_risk_change


同一个机会跨周出现时，更新“证据如何变化”，而不是重新写成一个新点子。


当系统运行 4 周后再考虑升级：
- 把 Opportunity Pool 从 Docs 迁移为 Google Sheet 或数据库，Docs 继续保存人类可读报告。
- 增加自动 experiment runner。
- 增加邮件/访谈/landing page 等外部动作前的人工审批闸门。
- 用历史 Judge 决策和真实实验结果校准评分权重，而不是凭感觉长期固定权重。


16. Recommended First Version


第一阶段只启用 8 个任务：3 个 Gemini Scouts + 3 个 GPT Scouts + Daily Integrator + Weekly Judge。
Experiment Designer 可以创建，但先保持暂停；当连续运行 2–4 周、确认信号质量和去重逻辑稳定后再启用。


系统的成功指标不是“发现多少机会”，而是：
1. 每月出现多少个拥有 >=3 个独立证据的机会。
2. Watch → Validate → Experiment 的转化率。
3. 被快速 Kill 的比例和平均耗时。
4. 实验产生真实外部行为证据的比例。
5. 一个季度后，有多少机会仍然成立。




17. Deployment Reliability — Gemini → GPT Handoff


重要修正：不要把“Gemini Scheduled Task 一定能直接创建、移动并归档 Google Docs”当成系统前提。Gemini Schedules 可以使用已连接的 Google Workspace，但 Google Workspace Connected App 对 Drive 内容管理存在能力边界；因此必须设计降级通道。


推荐顺序：
1. Direct Doc：如果当前 Gemini 账户实测能在定时任务中创建或更新 Google Doc，则继续使用 OR-GEMINI-* 文件命名，并让 GPT 从 Drive 读取。
2. Gmail Handoff（推荐稳定方案）：Gemini 定时任务将完整结果发送到自己的 Gmail，主题严格使用 OR-GEMINI-DEMAND-YYYY-MM-DD、OR-GEMINI-YOUTUBE-YYYY-MM-DD、OR-GEMINI-GEO-YYYY-MM-DD。GPT Ingestor 读取这些邮件，转换成 Shared Opportunity Card Schema，然后创建对应 Google Doc 并写入 10_Gemini 目录。
3. 如果 Direct Doc 与 Gmail 都不可用，则停止该 source，当天在下游标记 source_missing，不允许人工猜补。


Gemini 邮件输出必须是完整结构化结果，而不是“去 Gemini 查看详情”的摘要。正文第一行写 schema_version: OR-1；后续所有 Opportunity Card 保持与本文件第 3 节一致。


建议先 Run now 做 1 次能力探测：要求 Gemini 创建一个名为 OR-HANDOFF-TEST 的 Doc；若失败，再测试发送主题为 OR-HANDOFF-TEST 的自邮件。只保留通过实际测试的通道。


18. ChatGPT Task Slot Constraint & Deployment Plan


当前 ChatGPT 账户的 Active Task 槽位已达到上限，因此第一阶段不要为每个 Scout 单独占一个 ChatGPT Task。先采用任务合并策略：


A. Gemini 侧：保留 3 个独立 Sensor，因为 Google 生态内的 Search / YouTube / Geo 信号差异明显，且 Gemini 当前最多可支持更多独立 schedule。


B. GPT 侧合并为 2 个 Active Tasks：
- GPT External Scout：一次运行内依次扫描 Reddit、App Store、GitHub，分别创建 OR-GPT-REDDIT-*、OR-GPT-APPSTORE-*、OR-GPT-GITHUB-* 三个 Doc。三类信号仍独立分析，不在 Scout 阶段混合评分。
- GPT Opportunity Judge：读取当天 3 个 Gemini + 3 个 GPT source，先完成 Daily Integrator 的去重/证据归一化，再在每周指定运行中执行 Weekly Judge。若调度系统不适合一项任务同时承担 daily + weekly，则优先保留 Weekly Judge，Daily Integrator 可在 Judge 内回溯最近 7 天原始 source。


更推荐的 V1 是低频而高质量：Gemini 每日感知；GPT External Scout 每日或工作日运行；Weekly Judge 每周六运行。无需为了“每天有 Pool”额外占一个任务槽位。


19. Consolidated GPT External Scout Prompt


任务名：Opportunity Runtime — External Scout
建议频率：每天 07:15，或工作日 07:15


读取当天已有 OR-GEMINI-* 文档仅用于避免重复搜索，不把其中结论当作你的证据。然后独立执行三个扫描：


Part A — Reddit Pain Scout
遵循第 8 节规则。输出最多 8 个候选到 OR-GPT-REDDIT-YYYY-MM-DD。


Part B — App Store Friction Scout
遵循第 9 节规则。输出最多 6 个候选到 OR-GPT-APPSTORE-YYYY-MM-DD。


Part C — GitHub Momentum & Gap Scout
遵循第 10 节规则。输出最多 6 个候选到 OR-GPT-GITHUB-YYYY-MM-DD。


必须保持三个输出文件分离。不要因为同一机会跨三个来源出现就提前提高评分；跨源合并只由 Judge 完成。每个 Part 独立失败不影响其他 Part，失败时创建对应文件并写 source_status: failed + 原因。


20. Lean Weekly Judge Prompt


在 ChatGPT Task 槽位有限时，Weekly Judge 不依赖 Daily Pool。每周六读取最近 7 天全部 OR-GEMINI-* 与 OR-GPT-* source，直接执行：


1. Canonicalize：按 audience + JTBD 合并机会。
2. Deduplicate：去掉转载、同源派生和同一事件的重复证据。
3. Evidence Matrix：为每个机会分别统计 Demand / Pain / WTP / Supply Gap / Platform Shift。
4. Evolution：标记 New / Strengthening / Stable / Weakening / Falsified。
5. Score：使用第 12 节 100 分模型，但 Evidence Quality 是硬门槛而非普通加分项。
6. Decision：Experiment / Validate / Watch / Kill。
7. 每周最多批准 1 个 Experiment；允许 0 个。


输出 OR-JUDGE-YYYY-Www。系统优先追求“减少错误实验”，而不是“增加候选数量”。
